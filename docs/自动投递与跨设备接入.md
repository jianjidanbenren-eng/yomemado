# 自动投递与跨设备接入｜给部署者和接手的小机

这是一份按需阅读的进阶说明；普通部署与换图只需看[使用说明](../template/USAGE.md)。

公开模板可以直接部署使用。本说明把私人版已经验证的投递、在线读信方法整理成可复用步骤；后端源码、账户、存储与定时任务不随模板分发，需要在部署者自己的环境配置。只想手动增加来信，可以继续编辑 `template/letters.js`，不必接后端。

先读 [模板使用说明](../template/USAGE.md)、[制票流程](../template/USAGE.md#制作邮票) 和 [行为对照](../template/USAGE.md#收信与阅读)。接入只增加数据通道，保留现有 W32 音效、写字节奏、W38/W41 布局和邮票 PNG。

## 1. 先选需要的能力

| 能力 | 公开模板现在有什么 | 需要另外接什么 |
| --- | --- | --- |
| 手动更新来信 | 修改 `letters.js` 和正反面 PNG，重新部署 | 无 |
| 定时采风、制票、投递 | 可复用 Skill、规则、提示词、制票与检查脚本 | 能在网页关闭时运行的云任务、资料/图像工具、受限写入接口 |
| 手机与电脑读到同一批新信 | 当前默认读取随仓库发布的样例 | 持久存储、同一发布索引、只读接口、前端读桥 |
| 最新信的个人阅读/收藏跨设备同步 | 当前只在各浏览器的 `localStorage` 保存 | 登录、按用户隔离的状态数据库、状态接口、冲突处理 |

**“所有设备读到同一批来信”与“个人阅读/收藏记录同步”是两件事。** 私人版已验证前者，个人手动入藏与阅读记录仍按浏览器保存。藏信中的 READ 是约定的展示规则，不是服务器记录的真实阅读证明。

普通部署者可以停在第三项，不必为个人状态另建账号系统。下文第 8 节的个人状态同步是可选设计，尚未在此公开模板实现。

## 2. 谁负责什么

| 部分 | 职责 | 应保存什么 |
| --- | --- | --- |
| 制票 Skill | 核实地点和来源，制作画芯、正文和正反面 | 来源记录、完整地名、制作数据、检查结果 |
| 云定时任务 | 到点运行、选择未重复的地点、调用制票和投递、验收 | 日程、时区、任务提示词、运行结果；不保存访问密钥 |
| Site 后端 | 候选校验、发布、读取、撤回、权限 | 来信完整数据、候选哈希、有效发布索引 |
| Site 的 MCP / 插件连接 | 让小机调用同一后端的投递工具 | 接口声明与连接配置；不另写一套页面规则 |
| Site 前端 | 读信、地图计数、出票、逐字写信、入藏 | 当前来信列表；本地偏好与尚未接云端的个人状态 |
| 部署者自己的存储 | 长期保存数据与可回退版本 | 图片、候选、已发布记录、备份 |

新增来信通常只更新后端数据和索引，无需重新部署页面。改变读桥、权限或交互规则时，才修改并重新发布原站点。已有站点就修改原站点，不要另建一个替代站。

## 3. 接入前填写配置单

以下是接手时需要核对的项目，**不是当前 `config.js` 已支持的配置字段**。不要把表里的名称直接塞进配置文件就宣称完成了接入。

| 项目 | 要填写或核对的内容 |
| --- | --- |
| 目标站点 | 部署者自己的站点标识、源码位置、固定正式入口 |
| 访问范围 | 公开来信或私人信箱；保持原有访问范围 |
| 底版来信 | 已随页面提供的 ID；公开示例为 001–003，不重复发布这些 ID |
| 来信存储 | 私有持久对象存储；Sites 可绑定 R2，示例绑定名 `BUCKET` |
| 只读接口 | 与页面同源的地址；私人版路径约定为 `GET /api/private/letters` |
| 投递接口 | 部署者自己站点的 `POST /mcp`，或等效的受保护服务接口 |
| 写入者 | 服务端允许的写入身份；私人实现使用 `WRITER_EMAIL`，公开仓库不填写真实值 |
| 云任务 | 使用者希望的频率、时间、IANA 时区、任务连接与失败报告方式 |
| 前端接入 | 数据读取必须在 `machine.js` 首次初始化之前完成 |
| 可选个人同步 | 身份提供方、服务端用户 ID、状态表与冲突策略 |

[GitHub Pages 是静态托管](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)，不能因为仓库里增加了 `worker/` 就自动运行后端。要保留 Pages，可另外部署自己的后端；私人信箱优先使用有受保护同源路由的托管环境，减少跨站登录问题。部署按钮启动的仍是静态模板。

### 使用 ChatGPT Sites 时

1. 读取当前 Sites skill 和目标站点信息，打开该站点自己的源码，保留项目身份及访问范围。
2. 为持久存储声明 R2 绑定，服务端配置写入身份等运行时值；若还需结构化个人状态，可另外配置 D1。不要复制作者的绑定标识、账户或数据。
3. 实现 Worker 的只读路由与投递工具；需要 MCP 时，在托管配置的 capabilities 声明 `mcp`，按当前 Sites skill 发布并连接平台提供的 Site 插件。
4. 分别验证“能读取源码”“能调用工具”“有权写入”“浏览器能读到完整来信”，这几项不能相互替代。
5. 定时任务必须能在新的云任务上下文取得受支持的连接。只在当前聊天或本地预览能调用，不算无人值守接通。

在其他平台部署时，采用该平台受支持的存储、身份和调度方式。Sites 注入的身份头和门禁规则不能直接移植到一个裸露的公网 Worker。

## 4. 自动投递：先跑通一封，再设日程

### 一封信的数据

正式编号采用三位数字，测试件标明 `testOnly: true`，不得参与正式地图、最新信或旧信自动归档。公开模板只展示非测试的三位数字正式来信。下面是结构示意；图片占位符不能直接提交：

```json
{
  "id": "004",
  "date": "2026-10-30",
  "title": "核实后的地点短名",
  "place": "完整地点名",
  "region": "城市、地区、国家",
  "paragraphs": ["第一段短笺。", "第二段短笺。"],
  "signature": "—— 你的落款",
  "latitude": 0,
  "longitude": 0,
  "mapX": 50,
  "mapY": 50,
  "frontImage": "data:image/png;base64,<完整正面PNG>",
  "backImage": "data:image/png;base64,<完整背面PNG>",
  "testOnly": false
}
```

日期和坐标仅为结构示意，必须替换为实际寄出日期与核实坐标，不能沿用 `0,0` 充数。公开静态历史样例允许未知经纬度为 `null`，不能据此宣称它通过了私人投递器的坐标校验。

私人版投递器使用内嵌 PNG，要求正反面各 736×1040、8-bit RGBA、非交错，且齿孔 Alpha 完全一致。公开模板目前使用相对图片路径，`machine.js` 不接受上述 data URL 作为图片地址。因此接入者必须明确选择：将图片写为受控同源资源并映射成合法 URL，或修改图片 URL 校验以仅接受校验过的 PNG data URL。不可只复制 JSON 就认为兼容。

### 接口顺序与参数

这些是私人版同一后端已经采用的 MCP 工具名称与参数约定，供实现自己的接口时参考；它们不是公开仓库已经运行的服务。

| 顺序 | 工具 | 参数与作用 |
| --- | --- | --- |
| 1 | `get_delivery_status` | 无参数；读取有效编号，确认写入者已配置且当前调用者有权写入 |
| 2 | `upload_letter_chunk` | `id, index, total, dataBase64`；只暂存，不发布 |
| 3 | `finalize_letter_candidate` | `id, total, sha256`；拼接、核对哈希和格式，生成候选 |
| 4 | `get_letter_candidate` | `id`；读回候选的哈希、大小、地点和图片校验摘要 |
| 5 | `publish_letter_candidate` | `id, sha256`；核对候选后，更新已发布数据与索引 |
| 6 | `get_delivery_status` + 正式网页 | 索引包含新 ID；正式页面能取信、读背面和下载完整 PNG |
| 失败时 | `rollback_last_letter` | `id, sha256`；仅允许撤回发布索引中最后加入的那一封 |

实现时保留这些约束：

- 使用待传输的**最终 UTF-8 JSON 字节**计算 SHA-256，再切分字节；每块单独 Base64 编码，`index` 从 0 开始。不要先切中文字符串，也不要在计算后重新格式化 JSON。
- 私人实现每块最多 240,000 个 Base64 字符，最多 64 块，完整候选最多 10,000,000 字节。读取一次最多 50 条增量记录，需更多时另行设计分页，不得静默丢信。
- 新信采用下一个未占用正式编号；重试同一候选时保持相同 ID 与哈希。相同内容重复发布应返回幂等成功，不增加点位。
- 纠正已暂存候选时，需要读回旧哈希，并以 `replaceSha256` 显式指定。对于已经上线的同编号修正，先备份已发布正文和元数据，再设计一致的替换与恢复步骤，不能直接覆盖候选元数据导致在线读信哈希失配。
- 对发布索引的写入要串行或采用存储支持的原子条件更新。私人方案主要服务单一写入者；普通“读索引再覆盖”不是多任务并发保障。
- 发布索引最后更新，读回必须核对新 ID 和完整数据。回滚后从索引消失，不等于对象已删除；清理和保留期限由部署者另行设置。
- 只有最后一封可以按上述接口回滚。若后续已加入别的信，停止自动撤回，交由部署者处理，避免误撤后来信。

### 设定时任务

先手动完成一次“生成 → 暂存 → 校验 → 发布 → 正式网页验收”，再用相同连接验证一次新的云任务能执行。重用已有测试结果和候选，不重复制造正式来信。

创建前查询已有任务，避免同一站点同一时段重复寄信。示例频率可设为每周二、周五 10:00，时区 `Asia/Shanghai`；这是可调整的范例，不会自动创建任务。当前调用环境若没有排程工具，就交付提示词并说明日程尚未建立。

任务运行在网页之外，不能用页面 `setInterval` 代替。正常任务按日程读取已发布索引并选择下一编号；失败后重跑同一候选，不能靠跳号或换站掩盖失败。报告应区分“日程已保存”“后台已发布”“网页已验收”。

## 5. 在线读桥：所有设备取得同一批信

### 服务端必须先确认权限

私人信箱的只读接口复用托管平台已经验证的所有者访问门禁。`worker/index.ts` 的路由与 `worker/delivery.ts` 的读取处理必须一致：已通过门禁的普通浏览器，不应再被要求带上 MCP 写入者的额外身份头。投递、定稿、发布和撤回仍保留服务端写权限检查。

这个做法仅适用于**已确认在外层受保护的私人站点**。自建公网接口必须自行验证会话或令牌；不能简单删除身份判断，更不能信任客户端自填的 `oai-authenticated-user-*` 头。公开来信可允许匿名读取，但写入仍需保护。私人和公开来信不能混用同一份可公开索引。

读接口只返回已定稿且已发布的完整来信，不能返回暂存候选。应检查有效编号、重复记录、元数据、哈希、必填字段、地图坐标和图片条件；失败给出错误响应，而不是 `200 {"letters":[]}`。私人响应使用 `Cache-Control: private, no-store`。

成功响应约定为：

```json
{"letters": []}
```

上面是没有增量时的有效响应形状；有新信时，数组元素必须是第 4 节的完整对象，且不包含底版 ID。前端应校验完整批次后再合并，任何一条失败都不能先塞入半批数据。

### 前端的 v13 行为

1. 启动时读取底版，再 `GET` 同源只读接口，设置 `credentials: 'include'`、`cache: 'no-store'` 和 `Accept: application/json`。
2. 每次请求六秒超时，最多三次；两次重试前分别等待 900ms、1800ms。
3. 验证增量记录：正式 ID 不重复底版或其他增量，必填字段齐全，地图点位 0–100，图片有效。成功后一次合并，再初始化地图、索引、最新信和藏信。
4. 连续失败保留底版可用，同时显示 `SYNC ERROR · 在线来信读取失败，请刷新后重试`。点地图或打开藏信触发重绘后，错误也必须保留。
5. 记录诊断状态、尝试次数、HTTP 状态和失败阶段；不要记录私人正文、图片字节、凭据或身份资料。私人版诊断入口为 `window.__YOMADO_FEED_DIAGNOSTICS__`。

**当前公开模板没有启用这段读桥，也没有 `feedUrl` 配置开关。** 接入者需要把前端入口改为先完成异步读取，再执行现有 `machine.js` 初始化。该脚本会立即生成 `letters`、`lookup` 和点位，启动后只修改 `window.YOMEMADO_LETTERS` 不会自动刷新这些对象。页面底部脚本顺序与图片格式映射都要一并处理。

保持固定正式入口，不通过换链接或加刷新参数掩盖读取故障。新的来信在打开或刷新时出现；若希望已打开页面自动更新，可另加有节制的恢复焦点刷新，并处理正在出票/书写时的数据切换，这不属于现有默认功能。

## 6. 收信、已读和藏信始终遵守同一规则

| 场景 | 地图 | 藏信 |
| --- | --- | --- |
| 三封正式信，最新未手动入藏 | 03 | 001、002 两枚，均 READ / 已读 |
| 只翻阅最新 003 | 仍 03 | 仍为两枚，不因阅读自动收藏 |
| 手动入藏 003 | 仍 03 | 三枚，均已读；刷新保留记录 |
| 正式 004 抵达，004 未手动入藏 | 04 | 旧 001–003 三枚已读 |
| 七封正式信，最新未手动入藏 | 07 | 六枚旧信已读 |

按有效正式列表计算数量，而不是用最大编号代替数量；藏信按编号倒序。测试件不参与，撤回后重算。同编号换内容时，个人标记必须绑定内容版本；公开模板当前标记包含编号、日期、地点、标题和图片路径，覆盖图片时需更新路径或版本参数。已由使用者手动收藏的最新信不能被重置，以伪装成 N−1 的初始状态。

## 7. 必须实际检查，再报告完成

在测试记录中填入“实际环境、入口、索引、页面数量、交互、结果”，不要预填通过：

| 检查 | 应有结果 |
| --- | --- |
| 桌面浏览器与手机普通浏览器，打开同一正式入口 | 读取相同有效正式 ID 与数量；手机真机检查不能由窄屏模拟替代 |
| 若还支持 App 内打开 | 同入口同结果，分别记录；不以 App 内成功代替普通浏览器 |
| 旧浏览器与新的浏览器存储 | N 封时，未收藏最新信的环境有 N−1 枚旧信已读；有历史手动收藏的按真实状态显示 |
| 新信的交互 | 地图点位正确、出票、取信、翻面写字、原音效、完整正反面下载、手动入藏均可用 |
| 无权访问与无权写入 | 私人数据不可匿名读取；普通读取者不能进行写操作 |
| 暂时失败后恢复 | 最多三次重试，恢复后只合并一次 |
| 持续超时、401/403、损坏数据 | 显示同步失败，重绘不抹掉；不把底版点数报告为最新信箱 |
| 同一候选重复发布 | 无重复索引、地图点位或藏信 |
| 测试与撤回 | 不污染正式计数；旧信仍可取出和阅读 |
| 新的云任务上下文 | 无需沿用本次聊天临时凭据，就能取得连接、运行和读回 |

后端显示新增了三封而任一设备仍只有三枚底版时，继续查读桥，不能报告跨设备修复完成。若拿不到手机真机，就明确写“桌面通过、手机待验证”。

### 常见故障的定位顺序

| 现象 | 下一步 |
| --- | --- |
| 401/403 或返回登录 HTML | 查站点门禁、顶层登录和服务访问；不要关闭私人访问控制来“修复” |
| 404 | 查 Worker 路由、部署根路径、同源地址与实际托管能力 |
| 503 `r2_read_failed` | 查存储绑定、索引与对象是否存在 |
| 503 `json_validation_failed` | 查 JSON、候选元数据、哈希、字段和图片；不修改前端伪造点数 |
| JSON 正确但仍显示底版 | 查异步初始化顺序、批次校验、图片 data URL/资源 URL 适配 |
| 部分设备正常、部分只有底版 | 查同一入口、登录、Cookie、缓存、请求状态与诊断；分别实测 |
| 地图一致但最新收藏不一致 | 默认本地状态的预期行为；只有另接第 8 节后才验收个人同步 |

## 8. 可选：个人阅读/收藏记录真正跨设备同步

这是后续实现方案，不是本仓库已有接口，也不是私人版已经完成的能力。仅当部署者需要时再做。

- 使用服务器验证的稳定用户 ID；Sites 可用同一 Site 内的 `oai-authenticated-user-id`。邮箱用于展示，不作为永久数据库主键。浏览器不能代填用户 ID 来读取其他人的记录。
- 状态按 `(site_id, user_id, letter_id, letter_version)` 唯一保存，字段可含 `read_at`、`manual_collected_at`、`revision`。版本应绑定正文、图片或它们的内容哈希，避免新内容继承旧标记。
- 可自行实现 `GET /api/me/letter-state` 和 `PATCH /api/me/letter-state`。这些是建议路径；服务端检查登录、用户归属和有效来信，写请求防跨站伪造，返回私有且不缓存的响应。
- 登录后先读云端，本地记录经用户明确选择后迁移或合并；退出后清空内存中的私人状态，匿名状态与已登录状态分开。
- 第一版可只支持增加阅读/收藏：同版本的有效已读或手动收藏合并为真，旧设备的 false 不覆盖云端 true。若增加取消收藏或清除记录，再加版本冲突检测、删除标记及明确的合并规则。
- 旧信自动归档是有效来信列表的派生规则，不给所有用户批量写“真实已读”。服务器主要保存最新信的个人动作，最终显示仍按第 6 节计算。
- 断网时可排队，但必须显示待同步，不能将本地成功冒充云端成功。同一账号手机收藏后，桌面恢复焦点/刷新可见；另一账号不可见。两台设备并发、离线重连、退出和同编号换图都需要测试。

若只完成第 5 节，就写“来信列表跨设备一致，个人状态按浏览器保存”。完成本节并实测后，才写“个人状态跨设备同步”。
