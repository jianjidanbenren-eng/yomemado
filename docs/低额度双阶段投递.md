# 低额度双阶段投递｜先准备，再发行

这是一种给“定时采风 → 制票 → 发布”流程减轻执行端负担的通用方法。

核心不是压缩成品质量，而是把工作拆成两段：

```text
准备任务（轻）
研究 / 选题 / 授权 / 构图 / 文案
        ↓
结构化 brief 队列
        ↓
发行任务（重）
读取 1 个 brief / 制票 / 上传 / 发布 / 一次验收
```

准备阶段把所有可以提前决定的内容做完；发行阶段不再重新研究、重新选图或重写文案，只负责把已经确认的 brief 变成正式来信。

> 这份方法只描述流程。公开模板本身仍是静态网页，不会因为加入本页就自动拥有后台、定时任务或写入能力。完整接入边界见[自动投递与跨设备接入](自动投递与跨设备接入.md)。

## 什么时候适合这样拆

适合这些情况：

- 自动发行环境的调用量、上下文或执行额度比普通聊天更珍贵；
- 每封信在发行前都要做地点研究、事实核对、素材授权、构图和文案；
- 发布动作本身已经稳定，不希望每次定时任务都重新做一遍前期工作；
- 希望失败时保留已经准备好的内容，而不是从选题重新开始。

如果只是手动偶尔加一封信，没有定时任务或执行额度压力，直接按[使用说明](../template/USAGE.md)操作更简单。

## 1｜准备任务：把脑力活做到 brief 里

准备任务负责：

1. 选定唯一地点与主题；
2. 核实坐标和少量关键事实；
3. 决定唯一主素材，并记录作者、许可和原始链接；
4. 写清裁切、焦点和画面要求；
5. 完成故事、背面短笺、到信提示和聊天介绍；
6. 需要生成画面时，在这里把最终生成提示词写定；
7. 将结果写成一个轻量 brief 入队。

准备任务**不**制作正式邮票，不上传正式来信，也不改正式发布索引。

为了避免研究无限扩张，可以给准备任务设硬边界，例如：

- 第一批只查事实；
- 第二批只补素材和许可；
- 一旦满足发行条件就停止；
- 不为了“也许有更漂亮的图”继续找第 N 个方案。

## 2｜一个够用的 `letter-brief.v1`

下面是推荐的最小结构。它只存“发行决定”，不存 PNG、Base64、整站 HTML 或其他大文件。

```json
{
  "schema": "letter-brief.v1",
  "brief_id": "stable-id",
  "place": {
    "full_name": "",
    "region": "",
    "country": "",
    "lat": 0,
    "lon": 0
  },
  "topic": "",
  "story": "",
  "fact_sources": [
    {
      "fact": "",
      "source": "",
      "url": "https://..."
    }
  ],
  "art": {
    "mode": "photo",
    "primary": {
      "page_url": "https://...",
      "original_url": "https://...",
      "author": "",
      "license": "",
      "license_url": "https://..."
    },
    "backup": null,
    "crop_note": "",
    "focal_point": "",
    "allow_generated_art": false,
    "generation_prompt": ""
  },
  "back_notes": ["", ""],
  "arrival_line": "",
  "chat_intro": "",
  "valid_until": "ISO-8601"
}
```

建议约束：

- `brief_id` 稳定；
- `fact_sources` 只留真正支撑这封信的少量来源；
- 背面短笺数量固定；
- `chat_intro` 控制长度；
- 摄影方案指定唯一 `primary`，只有技术失败才使用 `backup`；
- 生成方案的 prompt 在准备阶段定稿，发行阶段不再临场改写；
- brief 设置过期时间，避免很久之后用陈旧信息自动发行。

## 3｜图片也要做“单次读取”设计

图像输入不是免费的上下文。大图、多图和重复视觉检查都会增加输入处理；不同产品、模型和套餐的具体使用量计算可能变化，所以不要用“看起来只有一张图”来估算成本。

这套流程建议把图片处理拆成三层：

### 准备阶段：只做一次真正的视觉判断

- 候选图在准备阶段完成筛选；
- 最终只留下一个主素材 `primary`；
- 把已经确认的视觉判断写进 brief：主体、焦点、裁切、需要保留/去掉的元素、画面方向；
- 记录原图 URL、作者、许可和必要的资源标识；
- 有多个候选时，落选后就不要继续把它们带进发行上下文。

### 发行阶段：需要原图时只拿主素材

如果制票需要照片转绘或以原图为参考，发行任务仍然要取得那张主素材；但它不再做“这张好不好看”“要不要换另一张”的审美复查。

也就是说：

```text
不推荐：
读候选 A/B/C → 再读 A → 看截图 → 再读原图 → 再看成品截图

推荐：
准备阶段确定 A + 裁切/焦点
→ 发行阶段只取 A 一次用于必要的转绘/生成
→ 程序校验尺寸、Alpha、哈希和字段
→ 仅在真正需要视觉判断时看一次最终成品
```

### 能程序验证的，不再让模型看图

这些项目优先用程序或结构化数据验收：

- 图片尺寸与格式；
- Alpha/透明区域；
- 文件哈希与字节数；
- 正反面文件是否成对；
- 资源 URL 是否可读取；
- 编号、地点、日期和 JSON 字段是否一致；
- 正式索引是否包含新信；
- 页面是否拿到完整资源。

视觉模型留给真正需要视觉判断的事项，例如主体是否画错、构图是否偏离、文字是否明显溢出。不要为了证明“上传成功”连续截图。

## 4｜发行任务：只消费，不重新创作

发行任务启动后先取**一个**最早有效 brief。

如果：

- 没有 brief；
- brief 已过期；
- schema 不合格；
- 正式编号冲突；

就停止，不临时改成“那我自己再找一个地点”。

正常发行只做：

1. 读取一个 brief；
2. 取得真实下一编号；
3. 按 brief 制作邮票；
4. 本地校验最终 JSON / 图片；
5. 一次上传链；
6. 一次发布；
7. 一次最小线上验收；
8. 成功后把该 brief 标记完成；
9. 输出真正的到信消息。

失败路径也保持克制：先确认当前状态，再决定是否重试。状态未知时不要直接重新研究、生图、上传或部署。

## 5｜用轻量队列隔开两个任务

队列可以是数据库，也可以是一个支持状态的轻量存储。

一种零额外服务的做法是用私有 GitHub Issues：

- 一个 open Issue = 一封待发行 brief；
- 标题只用于排序和识别；
- 正文只存一个结构化 JSON；
- open = 待发行；
- closed/completed = 已发布并通过最小验收。

不要在队列里塞：

- PNG / Base64；
- 整个网页；
- 大段聊天历史；
- 多份候选图；
- 每轮都重新生成的完整中间产物。

队列的作用是**传决定，不是搬上下文**。

## 6｜不要把“运行更快”直接写成“省了 X%”

执行时间缩短通常是好信号，但它不是可靠的额度换算器。

真正应该观察的是：

- 发行任务是否还在重新搜索和选题；
- 同一张图片是否被重复读取；
- 是否反复生成同一画面；
- 是否重复上传、重复部署或连续截图；
- 是否一次只消费一个 brief；
- 失败后是否从已有状态恢复，而不是从头再来；
- 产品侧若提供 usage / token 明细，再用同类任务做前后对比。

在没有可比较的 usage 数据时，应该写“减少了哪些高成本步骤”，不要虚构一个百分比。

## 7｜推荐的两个定时任务

### A. 准备任务

频率可以比发行提前一天或数小时。

示例职责：

```text
准备下一封来信。
只做研究、素材许可核对、构图决定和文案，
生成 letter-brief.v1 后入队。
不制正式邮票、不发布、不部署。
满足发行条件后停止继续搜索。
```

### B. 发行任务

只做执行：

```text
读取最早一个有效 letter-brief.v1。
不要重新研究、选题、选图或润色。
严格按 brief 制票、校验、上传、发布并做一次最小验收。
成功后将该 brief 标记 completed。
失败时保留 brief，不从头重做。
```

准备和发行错开后，即使发行环境更昂贵，它也只承担真正必须在那里完成的工作。

## 8｜验收标准

这套方案跑通，不是看“任务显示完成”，而是同时满足：

1. 准备任务确实产出一个可直接发行的 brief；
2. 发行任务没有重新做准备阶段工作；
3. 图片没有被无意义重复读取；
4. 正式网页能看到新地点和新邮票；
5. 出票、翻面和下载仍正常；
6. brief 在成功后才标记完成；
7. 成品质量没有因为省额度而缩水。

省额度只是架构结果，**来信仍然要像一封真正的来信。**
